Документ описывает процессы, обеспечивающие поддержание жизненного цикла программного обеспечения
«Пир2Пир» (Pir2Pir), включая устранение неисправностей, совершенствование и обновление.

Процессы построены с учётом ГОСТ Р ИСО/МЭК 12207-2010 «Информационная технология. Системная и
программная инженерия. Процессы жизненного цикла программных средств».

---

## 1. Общая организация

Программное обеспечение предоставляется по модели SaaS: единственный действующий экземпляр
размещается на инфраструктуре правообладателя. Из этого следуют два обстоятельства, определяющие все
процессы ниже:

- обновления устанавливаются правообладателем и не требуют действий пользователя;
- у пользователя нет собственной установки, которую потребовалось бы сопровождать отдельно.

Сопровождение осуществляется правообладателем — Индивидуальным предпринимателем Искужиным Айгизом —
собственными силами. Привлечение сторонних организаций для сопровождения не требуется.

## 2. Устранение неисправностей

### 2.1. Приём обращений

| Канал | Адрес |
| --- | --- |
| Электронная почта поддержки | support@pir2pir.ru |
| Обращения по персональным данным | legal@pir2pir.ru |

Обращение регистрируется в день поступления. Срок рассмотрения — не более 30 дней с момента
получения.

### 2.2. Порядок работы с обращением

1. **Регистрация.** Обращение фиксируется с указанием даты, содержания и сведений, необходимых для
   воспроизведения неисправности.
2. **Классификация.** Определяется характер обращения: неисправность, вопрос по эксплуатации или
   предложение по развитию.
3. **Воспроизведение и диагностика.** Для неисправностей выполняется воспроизведение на тестовой
   среде, анализ журналов работы и определение причины.
4. **Устранение.** Вносятся изменения в исходный код, сопровождаемые автоматическими тестами,
   исключающими повторное появление неисправности.
5. **Проверка.** Изменения проходят автоматическую сборку и прогон тестов; после этого
   разворачиваются на промышленной среде.
6. **Уведомление.** Заявителю сообщается о результате.

### 2.3. Приоритеты

| Уровень | Признак | Срок реакции |
| --- | --- | --- |
| Критический | сервис недоступен или недоступна основная функция | в течение рабочего дня |
| Высокий | функция работает неверно, обходного пути нет | до 3 рабочих дней |
| Обычный | частные неудобства, есть обходной путь | до 30 дней |

## 3. Обновление программного обеспечения

### 3.1. Порядок выпуска

Разработка ведётся в системе контроля версий Git. Применяется модель продвижения изменений через две
ветви:

1. изменения вносятся и проходят автоматическую проверку в ветви разработки;
2. сборка выполняется однократно, образ помечается идентификатором фиксации изменений;
3. перевод в промышленную эксплуатацию выполняется продвижением того же самого образа — повторная
   сборка не производится, что исключает расхождение между проверенной и работающей версиями;
4. миграции схемы базы данных применяются автоматически при запуске, до начала обслуживания
   запросов.

### 3.2. Контроль качества

- автоматические тесты выполняются при каждом изменении; изменение не может быть переведено в
  промышленную эксплуатацию при неуспешном прогоне;
- изменения, затрагивающие структуру данных, сопровождаются миграциями с возможностью отката;
- состояние работающего экземпляра и его зависимостей контролируется служебными адресами проверки
  работоспособности.

### 3.3. Периодичность

Обновления выпускаются по мере готовности изменений. Плановые технологические перерывы не требуются:
обновление занимает несколько секунд и приходится на время низкой нагрузки. Установка обновлений на
стороне пользователя не выполняется — при следующем обращении к сервису используется актуальная
версия.

## 4. Совершенствование

Развитие программного обеспечения ведётся на основании:

- обращений пользователей, поступающих в поддержку;
- показателей использования, собираемых в обезличенном виде;
- изменений во внешних системах, с которыми взаимодействует платформа.

Изменения, затрагивающие обработку персональных данных, вносятся с одновременным обновлением
[правовых документов](/legal/consent/) и не вводятся в действие до их публикации.

---

## 5. Резервное копирование и восстановление

- база данных размещается на выделенном томе, независимом от жизненного цикла контейнера
  приложения;
- журналы работы сохраняются вне контейнера и сохраняются при перезапуске и обновлении;
- образы предыдущих версий сохраняются, что позволяет вернуться к любой ранее работавшей версии;
- восстановление после сбоя выполняется развёртыванием сохранённого образа и подключением тома с
  данными.

## 6. Информация о персонале

Сопровождение осуществляется правообладателем. Для выполнения работ требуются специалисты,
обладающие:

- навыками разработки на платформе .NET и языке TypeScript;
- опытом администрирования СУБД PostgreSQL;
- опытом эксплуатации контейнеризованных приложений в операционных системах семейства Linux.

Для эксплуатации программного обеспечения пользователями специальная подготовка не требуется:
интерфейс рассчитан на обычного пользователя браузера.
